# JWT / GraphQL / 请求走私 / 缓存投毒

> 目标：覆盖近年 CTF Web 中很高频、但传统知识库常写得过散的题型。重点不是死记 payload，而是快速识别“数据流边界”和“代理/后端不一致”。

---

## 1. JWT

## 1.1 识别特征
- 看到 `eyJ...` 三段结构字符串
- Cookie / Authorization 头里出现 Bearer token
- 题目出现 `role=guest`、`admin=false`、`uid` 等用户态信息
- 后端报错涉及 `alg`、`kid`、`jku`、`x5u`、`jwks`、`secret`

## 1.2 最短分析顺序
1. 解码 header / payload，看算法、关键字段、过期时间
2. 判断是对称签名还是非对称签名
3. 看服务端是否只校验“能解码”而不校验“合法签名”
4. 看是否存在：
   - 弱密钥
   - `alg` 处理错误
   - `kid` 文件/路径利用
   - `jku` / `x5u` 外部密钥加载
   - 签名与业务字段脱钩

## 1.3 CTF 中高频漏洞模型

### A. `alg` 处理错误
- 服务端错误地信任 token header 中的算法说明
- 识别点：修改算法字段后行为明显变化
- 关注：
  - 是否允许空签名
  - 是否把非对称场景错误转成对称校验

### B. 弱密钥 / 可爆破 secret
- 题目常把 secret 放源码、配置、环境变量、git 泄露、注释里
- CTF 中常用短 secret、单词、框架默认值

### C. `kid` 注入
- 服务端根据 `kid` 取本地文件 / 缓存项 / 数据库条目找密钥
- 核心不是“写特定 payload”，而是看：
  - `kid` 是否被当成路径/键名
  - 键查找有没有目录穿越或特殊文件回退
  - 空值/异常路径会不会触发固定密钥

### D. `jku` / `x5u` / `jwks` 远程密钥来源
- 如果服务端会根据 header 去拉外部密钥，题目常让你伪造自己的验证公钥
- 核心是“服务端是否把信任根交给了攻击者指定地址”

### E. 业务逻辑与签名脱钩
- 只校验 token 有效，不校验 token 中某字段与服务端 session / 数据库当前状态一致
- 常见如：
  - 修改 `role`
  - 修改 `uid`
  - 修改 `is_admin`
  - 越权访问他人资源

## 1.4 优先级
1. 先解码观察字段
2. 找源码、配置、泄露文件里的 secret
3. 再看 `kid/jku/x5u`
4. 最后才考虑更复杂的签名/密钥逻辑问题

## 1.5 常见误区
- 只盯着 `alg=none`
- 忽略业务字段和数据库侧校验是否脱钩
- 不检查是否可从 `.git`、备份、环境变量、报错里直接拿 secret

## 2. GraphQL

## 2.1 识别特征
- 端点常为 `/graphql`
- 请求体中有 `query`, `mutation`, `variables`
- 报错中出现 `Cannot query field`, `Introspection`, `__schema`

## 2.2 最短分析顺序
1. 先试 introspection 是否开启
2. 看 query / mutation 的对象模型
3. 看字段级鉴权是否缺失
4. 看分页、过滤、排序、嵌套深度是否可滥用
5. 看 debug/error 信息是否泄露内部 schema

## 2.3 高频漏洞模型

### A. Introspection 暴露
- 能快速拿到全部类型、字段、参数、mutation 名称
- 对小模型最有价值：可以据此生成“对象关系图”和攻击面索引

### B. 字段级鉴权缺失
- 接口层做了鉴权，但字段层没做
- 例如：普通用户能查到 `email`, `phone`, `apiKey`, `isAdmin`

### C. IDOR / 对象遍历
- `node(id:...)`, `user(id:...)`, `order(id:...)`
- GraphQL 因对象关系清晰，IDOR 特别高频

### D. 复杂度/深度滥用
- 嵌套层数过深
- 批量别名查询
- 造成 DoS 或大规模数据回收

### E. Mutation 逻辑漏洞
- 修改资料、绑定邮箱、重置密码、上传文件等 mutation 只做了表层校验

## 2.4 比赛操作顺序
1. 先 introspection
2. 建对象图：用户、订单、文章、评论、管理对象
3. 对所有“按 ID 取对象”的查询做越权测试
4. 检查 mutation 是否存在权限穿透
5. 关注 debug error 泄露

## 3. 请求走私（Request Smuggling）

> CTF 里常见的是“前后端解析不一致”，本质上是**代理认为一个请求结束了，但后端认为还没结束，或反之**。

## 3.1 识别特征
- 前端有代理 / 网关 / WAF，后端有应用服务器
- 不同路径返回头差异明显
- 题目提示“代理”“负载均衡”“缓存”“内网路由”
- 某些请求会异常卡住、拼接、跨用户串包

## 3.2 核心模型
- `Content-Length` 与 `Transfer-Encoding` 解析优先级不一致
- 头部重复/变形/空白符处理不一致
- 前后端对请求边界认知不同

## 3.3 在 CTF 中的利用目标
- 绕过前端鉴权访问后端私有路由
- 走到管理接口 / debug 接口
- 污染后续用户请求
- 打开缓存投毒前置条件

## 3.4 最短验证思路
1. 判断是否存在代理链
2. 构造边界不一致的最小测试请求
3. 观察：
   - 是否超时
   - 是否吞掉后续请求
   - 是否命中异常路由
4. 如果有证据，再转向：
   - 管理路径
   - 内网路径
   - 缓存键污染

## 3.5 误区
- 一上来就套固定 payload
- 不先确认目标是否真的存在多层代理/后端
- 不对异常响应做归因：超时、400、串包、缓存异常分别代表的现象不同

## 4. 缓存投毒 / 缓存欺骗

## 4.1 识别特征
- 响应头里有 `X-Cache`, `Age`, `Via`, `CF-Cache-Status` 等
- 同一路径多次访问响应头变化明显
- 代理/CDN 对 query / header / host / path 处理与源站不同

## 4.2 核心模型
- 缓存键包含的信息，比源站使用的信息少
- 或源站使用了某输入生成响应，但缓存层没把它纳入键

## 4.3 高频题型
### A. Host / X-Forwarded-* 参与源站渲染
- 页面中出现绝对链接、重置链接、资源 URL
- 源站使用 Host 生成内容，但缓存键不区分该头

### B. Query 参数被源站使用但被缓存忽略
- 某些参数只影响页面某部分渲染
- CDN/代理不把该参数纳入缓存键

### C. Header 驱动页面变体但不入缓存键
- 如语言、设备、调试、内部标志头

## 4.4 比赛思路
1. 先确认可缓存
2. 再找“源站使用但缓存层忽略”的输入
3. 看是否能反射到页面
4. 让他人访问同一路径时命中污染内容

---

## 5. 这四类题的统一思维

它们共同点不是语法，而是：

1. **边界错配**：客户端/代理/后端/缓存/业务对同一数据理解不同
2. **信任错位**：把 header / token header / schema / upstream 元数据当真
3. **键不一致**：鉴权键、缓存键、查询键、对象键不一致
4. **对象图可遍历**：GraphQL、JWT claims、缓存键、代理路由都可抽象成可遍历图

---

## 6. 赛中速查

### JWT
- 先看算法和 secret 来源，不要只盯 `alg=none`
- 重点检查 `kid/jku/x5u` 与业务字段越权

### GraphQL
- 先 introspection，再字段级鉴权和 IDOR

### 请求走私
- 先确认代理链，再验证前后端边界不一致

### 缓存投毒
- 先确认缓存存在，再找“源站用、缓存不看”的输入
