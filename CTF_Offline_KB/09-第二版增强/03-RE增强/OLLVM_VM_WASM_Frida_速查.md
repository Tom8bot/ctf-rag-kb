# OLLVM / VM / WASM / Frida 速查

> 目标：解决 RE 里“会基础静态分析，但一遇到混淆、虚拟机、WASM、移动端动态分析就掉速”的问题。

---

## 1. OLLVM（控制流平坦化、指令替换、虚假分支）

## 1.1 识别特征
- CFG 特别扁平，一个 dispatcher 控制大量基本块
- 大量 switch / state 变量跳转
- 同类算术被拆成奇怪位运算
- 存在明显不会影响语义的 bogus branch

## 1.2 最短处理顺序
1. 找 dispatcher/state variable
2. 恢复状态转移关系
3. 先做块级语义归纳，不要一条指令一条指令抠
4. 对关键 check 点做 patch 或动态跟踪

## 1.3 最有用的方法
- 画状态机，而不是盯 CFG 图形美观
- 识别“真正修改状态变量”的块
- 对 bogus branch 直接 patch 或在脑中忽略
- 对 MBA（混合布尔算术）优先简化成等价表达式

---

## 2. VM / 字节码解释器题

## 2.1 识别特征
- 程序核心是一个循环：取 opcode -> 分发 -> 操作虚拟寄存器/栈
- 存在自定义指令集
- flag 校验不是原生汇编逻辑，而是“解释器跑脚本”

## 2.2 解题顺序
1. 确认 VM 状态结构：pc、stack、regs、memory
2. 枚举 opcode 语义
3. 提取字节码
4. 写解释器/反汇编器
5. 把验证逻辑提升到 Python 层处理

## 2.3 高价值策略
- 不要手工单步整个 VM
- 先做 opcode 表
- 把字节码 lift 到可读 IR
- 若是校验题，很多时候直接符号化输入或逆执行比纯动态更快

---

## 3. WASM

## 3.1 识别特征
- 题目给 `.wasm` 或网页里加载 wasm 模块
- JS 调 `WebAssembly.instantiate`
- 校验逻辑藏在 wasm 而不在 JS

## 3.2 核心注意点
- WASM 是栈机
- 重点看：
  - 导入/导出函数
  - 线性内存
  - 表（table）
  - 数据段
  - 校验主循环

## 3.3 解题顺序
1. 导出 wat/伪代码
2. 定位输入进入点
3. 看内存布局和常量表
4. 还原比较/变换流程
5. 必要时自己写仿真器或直接 patch 返回值

---

## 4. Frida / 动态插桩

## 4.1 适用场景
- Android / iOS / Native / JNI
- 想快速绕过：
  - root 检测
  - SSL pinning
  - 某个校验函数
  - 某个加密函数输入输出

## 4.2 核心思路
- 不一定要完全逆向，只要能截到关键函数的参数、返回值、调用时机即可
- 对加密/编码类题，抓中间态常比硬逆算法更快

## 4.3 最常做的事
1. hook Java 方法
2. hook native 导出/符号
3. 打印参数和返回值
4. 直接改返回值或 patch 内存

---

## 5. 统一方法论

这些题的共同点是：
- 原始语义被包装了
- 你的目标是**恢复高层语义**，而不是沉迷底层噪音

### 统一处理框架
1. 先找输入位置
2. 找关键状态变量
3. 把复杂控制流抽象成状态机/解释器/变换链
4. 在高层重写逻辑
5. 必要时 patch / hook / dump 中间值

---

## 6. 误区
- OLLVM 题里执着于每条汇编
- VM 题里不写解释器，纯手推
- WASM 题只看 JS 不看 wasm 主体
- 动态分析题不做 hook，只硬啃静态逻辑
