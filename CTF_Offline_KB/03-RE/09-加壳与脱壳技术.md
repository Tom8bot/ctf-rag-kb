# 加壳与脱壳技术

## 1. 概述

加壳（Packing）是对可执行文件进行压缩或加密，并在运行时自行解压复原的技术。加壳的原始目的是缩小文件体积，但至今已演变为反逆向的核心手段之一。在CTF中，加壳程序的逆向需要先完成"脱壳"（Unpacking）——将运行时解压后的原始程序Dump出来，修复其导入表，才能进入常规分析流程。

脱壳的基本流程：
1. **查壳**：识别壳的类型和版本
2. **找OEP**：定位原始程序的入口点（Original Entry Point）
3. **Dump**：在OEP处将解压后的内存镜像导出为文件
4. **修复IAT**：重建导入表
5. **修复其他**：重定位表、TLS、资源节等

## 2. 核心原理

### 2.1 壳的工作流程

```
加壳程序启动流程：
1. 壳的加载器（Stub/EP代码）先运行
2. 壳代码解密/解压原始程序的各节区
3. 壳代码解析原始程序的导入表，动态加载DLL并填充IAT
4. 壳代码处理TLS回调和重定位（如果需要）
5. 壳代码跳转到OEP（原始入口点）
6. 原始程序开始正常执行
```

**壳的分类**：
- **压缩壳**：仅压缩代码/数据，不加密。如UPX、ASPack、FSG、nPack
- **加密壳**：压缩+加密+反调试。如ASProtect、Armadillo、Themida、VMProtect
- **虚拟机壳**：将原始代码翻译为自定义字节码，运行时由解释器执行。如VMProtect、Code Virtualizer

### 2.2 导入表（IAT）的工作原理

IAT（Import Address Table）存储导入函数的实际地址。壳通过以下方式重建IAT：

1. 解析原始PE的导入表（INT/IDT）获取需要的DLL和函数名
2. 调用 `LoadLibrary`/`GetProcAddress` 获取函数真实地址
3. 填充到IAT中

**脱壳后IAT修复的必要性**：Dump出的内存镜像中，IAT地址可能与实际PE文件中的偏移不一致（因为壳可能改变了IAT位置），需要修正IAT才能让脱壳后的文件正常运行。

## 3. 关键技巧与工具

### 3.1 查壳工具

| 工具 | 用途 | 特征 |
|------|------|------|
| **Detect It Easy (DIE)** | 查壳/编译器/链接器识别 | 支持自定义签名，离线可用 |
| **Exeinfo PE** | PE查壳利器 | 特征库丰富 |
| **PEiD** | 经典查壳工具（已停更） | 对老壳识别率不错 |
| **手动识别** | 检查节名、入口点代码模式 | UPX节名：'UPX0', 'UPX1'；入口点有 `pushad/popad` |

**查壳命令**：
```bash
# DIE命令行
diec.exe target.exe

# Exeinfo PE
exeinfope.exe target.exe

# 手动快速识别
strings target.exe | head -20
# UPX特征：字符串中包含 "UPX!"
# ASPack特征：节名 ".aspack" 或 ".adata"
```

### 3.2 OEP查找方法

找到OEP（原始入口点）是脱壳最关键的一步：

**方法1：特征定位 - ESP定律（UPX/ASPack）**
```
1. x64dbg加载程序，停在了壳的入口点
2. 观察：第一条指令通常是 pushad（保存所有寄存器）
3. 执行 pushad 后，ESP指向被保存的寄存器上下文
4. 在ESP指向的地址设硬件写入断点
5. F9运行，当程序恢复寄存器（popad）时会触发硬件断点
6. 此时距离OEP通常只有几条指令的距离
7. 通常看到 popad 后跟随 jmp xxx —— 这就是跳向OEP
```

**方法2：内存断点法（更通用）**
```
1. 加载程序后 Alt+M 打开内存窗口
2. 在 .text/.code 段（代码段）设内存执行断点
3. F9运行——壳解压完代码后，第一次执行代码段就会触发
4. 此时恰好到达OEP
```

**方法3：API断点法（加密壳/复杂壳）**
```
在关键API设断点，跟踪到壳解析完后：
- VirtualAlloc: 壳分配内存空间
- VirtualProtect: 壳修改内存保护属性
- LoadLibrary/GetProcAddress: 壳解析导入函数
- 最后一个 GetProcAddress 返回后，离OEP不远

x64dbg操作：
1. 符号窗口 -> 搜索 "VirtualAlloc" -> 设F2断点
2. 多次F9观察分配的区域
3. 当看到分配的区域被填满代码后 -> 对那片区域设内存执行断点
4. F9到达OEP
```

**方法4：trace定位法（对付难以手动跟的壳）**
```
1. 启动x64dbg，开启Trace（Ctrl+Alt+T）
2. 设置Trace条件：只记录call/jmp/ret等控制流转移指令
3. 运行一段时间后停止
4. 分析trace日志，找到最后几个call/jmp
5. 从最后的call/jmp设断点，缩小范围
```

**方法5：GetProcAddress断点法（对付强壳）**
```
1. x64dbg在 GetProcAddress 设断点
2. 运行到所有DLL函数解析完成
3. 在 GetProcAddress 返回后单步跟执行
4. 通常在最后一组 GetProcAddress 调用后，壳会做最后的清理
5. 然后跳转到OEP

在OEP附近，通常能看到一个 jmp eax 或 jmp [some_addr]
```

### 3.3 内存Dump

**使用x64dbg的Scylla插件**:
```
到达OEP后：插件 -> Scylla
1. Scylla自动检测OEP位置（"IAT Autosearch"）
2. 点击 "Get Imports" -> Scylla扫描并识别IAT
3. 检查是否有无效的导入（红色标记）
4. 点击 "Dump" -> 保存内存镜像为 dump.exe
5. 点击 "Fix Dump" -> 选择刚保存的 dump.exe
6. Scylla自动修复IAT生成 dump_SCY.exe
```

**使用LordPE或PETools**（传统工具）：
```
1. 在OEP处暂停
2. 打开LordPE -> 选择目标进程
3. 右键 -> "Dump Full" 或 "Dump Region"
4. 保存为 dump.exe
```

**手动Dump（无法使用工具时）**：
```
在x64dbg中：
1. 打开Memory Map窗口 (Alt+M)
2. 选择所有代码段和数据段 -> 右键 -> "Dump Memory to File"
3. 分别保存各段，然后用PE编辑器拼接

在gdb中：
gdb> dump binary memory dump.bin 0x400000 0x410000
```

### 3.4 IAT修复

Scylla（x64dbg自带）是IAT修复的标准工具：

**Scylla修复流程**：
```
1. 在OEP暂停（!!!重要：必须在OEP处Dump）

2. 插件 -> Scylla -> 自动识别以下参数：
   - OEP：原始入口点RVA
   - IAT Start/End：导入表的起始和结束RVA
   - IAT Size：导入表大小

3. "IAT Autosearch" -> 自动扫描IAT范围

4. "Get Imports" -> 解析所有导入函数
   - 绿色：正确识别的导入
   - 红色：无法解析的导入（需要手动修复）

5. 手动修复红色导入：
   - 检查是否真的是导入函数（右键 -> "Disassemble"）
   - 如果是，手动指定DLL和函数名
   
6. "Dump" -> 保存内存镜像
7. "Fix Dump" -> 选择合适的DUMP文件
8. 测试修复后的exe是否能运行
```

**手动IAT修复**（当Scylla无法自动处理）：
```python
# 使用pefile库手动重建IAT
import pefile

def show_imports(pe_path):
    pe = pefile.PE(pe_path)
    if hasattr(pe, 'DIRECTORY_ENTRY_IMPORT'):
        for entry in pe.DIRECTORY_ENTRY_IMPORT:
            dll_name = entry.dll.decode()
            print(f"\n[{dll_name}]")
            for imp in entry.imports:
                name = imp.name.decode() if imp.name else f"ordinal({imp.ordinal})"
                addr = imp.address
                print(f"  0x{addr:08X}: {name}")

# 使用
show_imports("dump_SCY.exe")
```

### 3.5 UPX手动脱壳流程

UPX是最常见的加壳工具，有自动脱壳命令。但手动脱壳是CTF的基础技能：

```bash
# 方法一：自动脱壳（如果有网络/安装了UPX）
upx -d target.exe -o unpacked.exe

# 方法二：UPX静态脱壳（无UPX工具时）
# UPX压缩的数据在.UPX1节，算法主要是：
# 1. NRV压缩（LZMA的一种变体）
# 2. LZMA
# 可以用upx_unpacker Python脚本静态解压

# 方法三：手动动态脱壳（CTF最常用）
# x64dbg操作：
# 1. 加载target.exe -> 看到 pushad（入口点特征）
# 2. F8单步执行 pushad
# 3. ESP指向的位置 右键 -> "Follow in Dump"
# 4. 在Dump窗口选中4字节 -> 右键 -> "Breakpoint" -> "Hardware, Access" -> "DWORD"
# 5. F9运行 -> 断在 popad 后面的指令
# 6. F8单步 -> 看到 jmp xxx -> F8单步 -> 到达OEP
# 7. 插件 -> Scylla -> Dump + Fix Dump
```

### 3.6 应对反Dump保护

某些壳会防止你dump内存：

**反Dump手段及绕过**：
```
1. 代码段解密后立即重新加密（执行后擦除）
   -> 在OEP处暂停时，代码已解密，直接Dump即可

2. IAT动态调用（不通过标准IAT表，而是壳自己动态解析API）
   -> 这种情况Scylla可能识别失败，需要手动追踪API调用

3. 内存访问保护异常（利用SEH/VEH）
   -> 在异常处理中解密代码，执行后触发新的异常
   -> 绕过：在关键异常处理函数设断点，或使用PhantOm插件隐藏调试器

4. 检测内存完整性
   -> Dump后程序发现自己被改动，退出
   -> 需要额外Patch检测逻辑

5. RWE（读-写-执行）内存块
   -> 壳可能在堆上解密代码然后执行，OEP不是标准地址
   -> 需要跟踪内存分配和写入，识别动态代码段
```

## 4. 常见壳的特征与专门脱壳方法

### 4.1 UPX

```
特征：
- 节名：UPX0, UPX1, UPX2（或 .upx0, .upx1）
- 入口点：pushad 开头（大多数版本）
- 字符串："UPX!" 在近末尾

脱壳方法：
- UPX -d 自动脱壳（最快）
- ESP定律法（pushad -> popad -> jmp OEP）
- UPX -d 即使成功也可能被UPX的LZMA变体打败
  → 这种情况用x64dbg手动脱壳
```

### 4.2 ASPack

```
特征：
- 节名：.aspack, .adata
- 入口点：pushad / call (自修改代码)
- 压缩算法：aPlib (LZ77变体)

脱壳：
- ESP定律法同样有效
- 或者用 aspackdie 工具自动脱
```

### 4.3 Themida/WinLicense

```
特征（强壳）：
- 虚拟机保护字节码（VMProtect类似的VM）
- 多线程反调试
- 代码片段加密/解密
- 入口点混淆极强

应对策略（CTF场景，题目通常会降低难度）：
1. 先用ScyllaHide的Themida Profile绕过反调试
2. 在VirtualAlloc/VirtualProtect设断点观察内存分配
3. 寻找可疑的 jmp/call 到动态内存区域
4. 在那些区域Dump代码
5. 如果用了VM保护，代码逻辑需要重新分析（参考第10章）
```

### 4.4 PECompact

```
特征：
- 节名：pec1, pec2
- 压缩算法：LZMA，有时带加密

脱壳：
- PECompact命令行：pec2unpack
- 或手动：在WriteProcessMemory设断点，跟踪写入的代码段
```

## 5. 常见误区与注意事项

- **误区**：以为脱壳后就是完整可运行的程序。脱壳+修复IAT后仍需检查TLS回调（在OEP之前执行）、重定位表（动态基址时）、资源节等。Scylla修复后的exe可能还需要手动微调。
- **误区**：ESP定律是万能OEP定位法。ESP定律只对使用pushad/popad保存恢复寄存器的压缩壳有效（UPX、ASPack、nPack等），对加密壳和VM壳无效。
- **注意**：x64程序调试时不能用ESP定律——x64没有pushad/popad指令。改用内存断点或API断点法。
- **注意**：Scylla修复的IAT有时会漏掉一些动态加载的DLL。测试脱壳后的程序，用DependencyWalker或Process Explorer查看缺失的导入。
- **安全注意**：在CTF中脱壳时，程序可能会加载恶意行为。务必在虚拟机中操作，做快照后调试。

## 6. 实战示例

### 示例：完整的脱壳实战（UPX + 自定义修改）

```
目标：upx_custom.exe - CTF中使用了魔改UPX（修改了magic字节使其无法被标准UPX识别）

步骤1：查壳
diec.exe upx_custom.exe
# 输出：UPX(0.0) [modified] -> 被修改过的UPX

步骤2：尝试标准UPX脱壳
upx -d upx_custom.exe
# 失败：upx: upx_custom.exe: CantUnpackException: file is modified/hacked/protected

步骤3：手动脱壳（x64dbg）
1. 加载 upx_custom.exe
2. 看到入口点指令：
    push rax  (!!!注意：x64没有pushad，改成了push多个寄存器)
    push rbx
    push rcx
    ...
3. 这一步就是保存上下文，等ESP定律的硬件断点
4. F8单步几个push后 -> 在RSP指向的地址设硬件写入断点
5. F9 -> 断在恢复寄存器的地方
6. F8 -> 看到 jmp rax -> F8 -> 到达OEP
7. 确认OEP：反汇编代码突然变得连贯（不再是一串数据）
   -> .text段：0x140001234

步骤4：Scylla脱壳
1. 插件 -> Scylla
2. OEP: 1234 (注意是RVA, 需要减去ImageBase: 0x140000000)
3. IAT Autosearch -> Get Imports -> Dump -> Fix Dump
4. 生成 upx_custom_dump_SCY.exe

步骤5：验证
1. 运行 upx_custom_dump_SCY.exe -> 正常运行
2. 用DIE再次检查 -> "Microsoft Visual C++ 2019"
3. IDA加载 upx_custom_dump_SCY.exe -> 此时可正常分析
```
