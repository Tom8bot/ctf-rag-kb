# 动态调试技术

## 1. 概述

动态调试（Dynamic Debugging）是在受控环境中运行目标程序并观察其运行时行为的技术。不同于静态分析"看代码推逻辑"的方式，动态调试可以直观地看到程序的实际执行路径、寄存器变化、内存操作，以及运行时才能确定的间接跳转目标。在CTF竞赛中，动态调试与静态分析交替使用是效率最高的分析策略。

动态调试的典型应用场景：
- 绕过反调试保护后观察核心逻辑
- 追踪加密/解密过程中的密钥生成和数据变换
- 快速确认分支条件，不需要逆向复杂的数学运算
- 验证静态分析推断的结论
- 在加壳程序中Dump脱壳后的内存镜像

## 2. 核心原理

### 2.1 断点的工作机制

**软件断点（INT3, 0xCC）**：
- 调试器在目标地址写入单字节 `0xCC`（x86 INT3指令）
- CPU执行到该地址时触发 `SIGTRAP`/`EXCEPTION_BREAKPOINT`
- 调试器捕获异常后暂停，并将原指令恢复
- 缺点：修改代码段内存，易被反调试检测；不适合ROM/代码完整性校验场景

**硬件断点（DR0-DR7）**：
- 利用x86调试寄存器，不修改代码段
- 4个断点槽（DR0-DR3），DR6存储状态，DR7控制模式
- 类型：执行断点（fetch）、读/写/读写数据断点（access）
- 优点：不写内存，难以检测（除少数通过调试寄存器检测的反调试手段）
- 限制：最多4个同时生效，精确断点仅支持1/2/4/8字节长度

**内存断点（Page Guard）**：
- 通过修改目标内存页的 `PAGE_GUARD` 保护属性
- 第一次访问时触发 `STATUS_GUARD_PAGE_VIOLATION` 异常
- 调试器捕获后重新设置保护，单步执行然后恢复
- 优点：可以断在大范围内存区域上

### 2.2 条件断点实现原理

条件断点需要调试器在每次断点触发时检查条件表达式，这涉及：
1. 断点触发（软件/硬件）
2. 调试器接管控制权
3. 解析并求值条件表达式（读取内存/寄存器）
4. 条件成立则停止；条件不成立则继续执行
5. 恢复程序上下文

**性能考虑**：条件断点在热路径上会严重拖慢程序（每次触发都有调试器-被调试程序的上下文切换）。对于高频执行的代码位置，应使用"写代码"的方式模拟条件断点（见3.3节）。

### 2.3 调试符号与源码映射

- **DWARF**（Linux ELF）：调试信息段 `.debug_info`、`.debug_line` 等
- **PDB**（Windows PE）：微软程序数据库文件，存储符号与源码映射
- 即使程序不包含调试信息，也可通过手动分析恢复符号并应用到调试器

## 3. 关键技巧与代码

### 3.1 x64dbg高级操作

**常用快捷键和操作**：

| 功能 | x32dbg/x64dbg操作 |
|------|-------------------|
| 运行到用户代码 | `Alt+F9` (从系统DLL返回) |
| 运行到指定地址 | `Ctrl+G` 输入地址，`F4` 运行到此处 |
| 追踪寄存器修改 | 右键寄存器 -> "Follow in Dump" |
| 条件断点 | 右键断点 -> "Edit" -> 输入条件表达式 |
| 记录跟踪（Trace） | `Ctrl+Alt+T` 打开Trace窗口 |
| 修改EIP/RIP | 双击寄存器或右键 -> "Set value" |
| 补丁程序 | 选中指令 -> 空格 -> 修改 -> `Ctrl+P` 导出补丁 |
| 硬件断点 | 右键 -> "Hardware, Access" -> 选择大小/类型 |
| 监视窗口 | 右键内存dump -> "Add to Watch" |

**条件断点表达式语法**（x64dbg）：
```
# 寄存器
eax == 0x1234
ecx > 0x1000 && edx < 0x2000

# 内存
[esp+4] == 0xDEADBEEF
byte:[ecx] == 'A'

# 字符串（注意转义）
strcmp(ecx, "flag")

# 计数（n是触发次数）
$breakpointcounter == 5  # 第5次触发时才停下
```

**Trace（指令跟踪）使用**：

Trace功能记录每条执行过的指令，适合事后分析控制流（尤其对混淆代码）：
1. `Ctrl+Alt+T` 打开 Trace 窗口
2. 设置起始和终止条件（可指定地址范围）
3. 运行直到停止
4. 导出Trace日志，用脚本分析指令序列

```python
# 分析trace日志的Python脚本
# 用途：统计最频繁执行的基本块，辅助识别热点路径
import re
from collections import Counter

def analyze_trace(trace_file):
    addresses = Counter()
    jumps = Counter()
    
    with open(trace_file) as f:
        prev_addr = None
        for line in f:
            # 匹配地址字段
            m = re.match(r'([0-9A-F]+)\s+.*', line.strip())
            if m:
                addr = int(m.group(1), 16)
                addresses[addr] += 1
                if prev_addr:
                    jumps[(prev_addr, addr)] += 1
                prev_addr = addr
    
    # 按频率排序输出热点地址
    for addr, count in addresses.most_common(20):
        print(f"0x{addr:X}: {count} hits")
```

### 3.2 GDB高级调试技巧

**GDB脚本化断点**（.gdbinit或即时输入）：
```bash
# 条件断点：第100次循环时停止
b *0x401234 if $rcx == 100

# 断点命令：自动打印信息并继续
b *0x401234
commands
  silent
  printf "encrypt_round %d: rdi=%s\n", $rcx, (char*)$rdi
  continue
end

# 单步追踪特定指令序列
define trace_range
  set $start = $arg0
  set $end = $arg1
  while $pc >= $start && $pc <= $end
    x/i $pc
    stepi
  end
end

# GDB Python插件
python
import gdb

class PrintArgs(gdb.Breakpoint):
    """断点触发时自动打印函数参数"""
    def __init__(self, location, num_args=4):
        super().__init__(location)
        self.num_args = num_args
    
    def stop(self):
        for i in range(self.num_args):
            reg_name = ["rdi", "rsi", "rdx", "rcx", "r8", "r9"][i]
            val = int(gdb.parse_and_eval(f"${reg_name}"))
            print(f"  arg{i}: 0x{val:x}")
        return False  # 不停止，继续执行

PrintArgs("*0x401234")  # main+0x34
end
```

**GDB查看反汇编**：
```bash
disas /r main          # 显示原始字节
disas /m main          # 混合源码（如果有符号）
x/20i 0x401000         # 查看20条指令
x/10gx $rsp            # 以16进制查看栈上10个8字节值
```

**GDB远程调试**：
在CTF的Linux环境下，可能需要远程调试：
```bash
# 目标机器
gdbserver :1234 ./binary

# 本地机器
gdb ./binary
target remote 192.168.1.100:1234
```

### 3.3 内存Dump与补丁技术

**在x64dbg中Dump内存**：
1. 在Memory Map窗口选中目标内存区域
2. 右键 -> "Dump Memory to File"
3. 保存为.bin文件供后续静态分析

**动态补丁（免重编译修改程序逻辑）**：
```asm
; 原指令
0x401020: jne 0x401080    ; 条件跳转：验证失败则跳走

; 补丁方案1：NOP掉条件跳转（始终通过验证）
0x401020: nop
0x401021: nop
; 补丁方案1对应机器码：0x90 0x90（需补6字节，原jne为6字节）

; 补丁方案2：反转条件
0x401020: je 0x401080     ; 改为相等时跳转
; 机器码：0x0F 0x84 -> 0x0F 0x85 改为0x0F 0x84

; 补丁方案3：无条件跳转
0x401020: jmp 0x401080
; 机器码：0xEB 0x5E（短跳转）
```

**x64dbg导出补丁**：
修改指令后，`Ctrl+P` -> 选择"Patch file" -> 导出修改后的二进制。

**GDB中的运行时补丁**（不修改文件）：
```bash
set {int}0x401234 = 0x9090  # 写入NOP
set $rax = 1                 # 修改寄存器值
jump *0x401050               # 跳转到任意地址
```

### 3.4 DBI（动态二进制插桩）入门

动态二进制插桩框架（如Pin、DynamoRIO、Frida）可在不修改二进制的情况下注入分析代码。

**使用Frida在CTF中追踪函数调用**（即使无网络也可使用Frida本地模式）：
```javascript
// frida-trace-template.js
// 用法：frida -f ./binary -l this_script.js --no-pause

// Hook 导入的函数
const modules = Process.enumerateModules();
for (const mod of modules) {
    const imports = Module.enumerateImports(mod.name);
    for (const imp of imports) {
        if (imp.name.indexOf("strcmp") !== -1) {
            Interceptor.attach(imp.address, {
                onEnter(args) {
                    console.log(`[strcmp] "${args[0].readCString()}" vs "${args[1].readCString()}"`);
                }
            });
        }
        if (imp.name.indexOf("memcpy") !== -1) {
            Interceptor.attach(imp.address, {
                onEnter(args) {
                    console.log(`[memcpy] dst=0x${args[0]} src=0x${args[1]} len=${args[2]}`);
                }
            });
        }
    }
}

// Hook 自定义地址（通过IDA分析确定的关键函数）
const target = Module.findBaseAddress("binary")?.add(0x1234);
if (target) {
    Interceptor.attach(target, {
        onEnter(args) {
            this.start = Date.now();
            console.log(`[encrypt@${target}] input=${hexdump(args[0], {length: 16})}`);
        },
        onLeave(ret) {
            console.log(`[encrypt] time=${Date.now() - this.start}ms`);
            console.log(`[encrypt] output=${hexdump(ret, {length: 16})}`);
        }
    });
}
```

### 3.5 时间旅行调试（Time Travel Debugging）

虽然完整TTD方案较重，但在gdb中可利用逆向执行简化：
```bash
# gdb内置的逆向调试（需要record模式）
record full        # 开启执行记录
continue           # 运行到某位置
reverse-stepi      # 逆向单步
reverse-continue   # 逆向运行到上一个断点
```

x64dbg也有Trace replay功能，可通过导出Trace日志后进行回放分析。

## 4. 常见误区与注意事项

- **误区**：断在 `main` 函数就算开始分析。程序可能在 `__libc_start_main` 和 `_init` 中就完成了关键初始化（如解密代码段），错过了就看不到了。
- **误区**：过度使用软件断点。在反调试检测较严格的目标中，优先使用硬件断点。
- **注意**：x86的 `rep stos/movs` 等字符串操作指令在单步时会"跳过"，单步步过（step over）可能需要多次按F8才真正跳出。
- **注意**：64位程序中，栈上的字符串参数不一定对齐到8字节边界，这是正常的。
- **调试器检测**：某些程序检测 `BeingDebugged` 标志位（PEB + 0x2），调试前需要用ScyllaHide或手动修改PEB绕过。

## 5. 实战示例

### 示例：利用动态调试追踪加密流程

**场景**：程序接受一个字符串输入，加密后与硬编码值比较。

**分析步骤**：
```bash
# 1. 启动x64dbg，加载程序
# 2. 在GetWindowTextA/scanf/fgets等输入函数设断点，找到输入接收点
# 3. 输入一组已知字符串（如 "AAAAAAAAAAAAAAAA"）
# 4. 在输入缓冲区设硬件写入断点，追踪哪段代码访问/修改了输入
# 5. 一旦在加密函数中发现输入数据被修改，设F2断点
# 6. 重启程序，观察每次断点触发时的寄存器/内存变化
# 7. 密集观察加密循环中的关键变换：
#    - XOR操作：记录XOR的key值
#    - S-Box查表：确认使用的算法（AES/DES等）
#    - 移位/旋转操作：记录轮数

# 伪代码级别的观察日志
# Round 0: input = "AAAA...", XOR with 0x55 -> 0x11... 
# Round 1: S-Box at 0x405000, input[0] = sbox[0x11] = 0x82
# Round 2: Shift left 3 bits, XOR with constant 0xB7E15163
# ...
# 结论：这是XTEA变种，正确还原密钥后即可解密比较值
```
