# 逆向总纲 / 静态动态分析

---

## 1. 总流程

```text
file -> strings -> 导入函数 -> 主流程 -> 找比较点 -> 还原算法 / patch / 动调验证 -> 写脚本还原 flag
```

### 小模型固定回答模板
1. 文件类型：ELF / PE / Mach-O / APK / pyc / js / wasm
2. 是静态还原还是动态跟踪更合适
3. 关键函数：输入、变换、比较、输出
4. 常量：表、key、轮常量、S-box、magic number
5. 最终策略：直接 patch / 脚本还原 / 动调拿中间值

---

## 2. 开局必做

### 2.1 基础命令
```bash
file target
strings -a -n 4 target | less
checksec --file=target
objdump -d -Mintel target | less
readelf -a target | less
```

### 2.2 先看这些线索
- 有没有 `flag`, `wrong`, `correct`, `success`
- 有没有 `strcmp`, `memcmp`, `strncmp`, `md5`, `sha`, `AES`, `RSA`
- 有没有异常常量：`0x9e3779b9`, S-box, base64 表
- 输入是 argv 还是 stdin
- 是否存在明显的加壳/自解密行为

---

## 3. 静态分析策略

## 3.1 先找主流程
- `main`
- 输入读取函数
- 校验函数
- 输出成功分支

## 3.2 找比较点
- `strcmp/strncmp/memcmp`
- 长度判断
- 循环末尾是否累积真假标志
- 分支汇总函数

## 3.3 找常量与表
- XOR key
- 字符替换表
- base64/base32/base58 表
- CRC / hash 多项式
- AES / DES / RC4 / TEA 特征常量

## 3.4 数据流思维
不要只看“这句像不像算法”，而要问：
```text
输入 -> 若干变换 -> 最终比较对象是什么？
```
如果你能拿到“最终比较前的结果”，基本就能反推。

---

## 4. 动态分析策略

## 4.1 什么时候该动调
- 静态流程太绕
- 有自修改 / 解密 / 反调试
- 需要看运行时解密后的字符串/代码
- 只需在比较前断下来看内存即可

## 4.2 常见断点位置
- 输入读取后
- 关键变换循环前后
- `strcmp/memcmp` 调用前
- 成功/失败分支

### gdb 最小动作
```gdb
b *main
b *strcmp
r
ni
si
x/s $rdi
x/s $rsi
x/32bx $rax
```

## 5. 题型分类

## 5.1 明文比较题
### 特征
- 输入后直接对比固定字符串
- 可能做了简单编码、异或、倒序、位移

### 解法
- 直接在比较点看目标值
- 或 patch 跳过比较拿后续 flag

## 5.2 简单算法题
### 常见变换
- xor
- add/sub
- rol/ror
- swap / reverse
- index-based 混淆
- 表查找

### 解法
- 抄出伪代码到 Python 还原
- 注意有时是“验证函数”，需要写逆过程或直接爆破每位

## 5.3 状态机 / VM / 字节码解释器
### 特征
- 巨大 switch
- opcode dispatch
- 指令数组
- 虚拟寄存器/栈

### 解法
- 先识别指令格式
- 写解释器 / tracer
- 看最终 compare 什么值

## 5.4 壳 / 自解密
### 特征
- 运行后内存和磁盘代码不同
- OEP 不明显
- 节区熵高
- strings 少

### 解法
- 动态 dump 解密后代码
- 找解密循环、解包结束点、跳转点

---

## 6. 识别常见算法的特征

## 6.1 XOR
- 单字节循环：`buf[i] ^ k`
- 重复 key：`buf[i] ^ key[i % n]`
- 常见与 add/rol 组合

## 6.2 RC4
- 256 大小数组
- KSA 初始化 `S[i]=i`
- 大量 swap

## 6.3 TEA / XXTEA
- 常量 `0x9e3779b9`
- 轮函数中左右移和加异或

## 6.4 AES
- 明显 16 字节分组
- S-box / Rcon / MixColumns 表
- 调库时可能直接看到 EVP/AES API

## 6.5 Base 编码
- 标准字符表常量非常明显
- 往往不是核心，只是外层包装

## 6.6 CRC
- 查表 256 项
- 多项式常量
- 结果多为 32/64 位

---

## 7. Patch 思维

### 7.1 何时 patch
- 题目只想拿通过分支内的 flag
- 算法太长但无需完整理解
- 需要绕过环境检测、注册检测、次数限制

### 7.2 常见 patch 点
- `jne -> je` / `jz -> jnz`
- 直接改返回值为成功
- NOP 掉退出/检测函数

### 7.3 注意
- CTF 中 patch 常可快速出结果，但若 flag 由算法生成，仍需要理解数据流

---

## 8. 从伪代码到脚本

### 推荐步骤
1. 复制核心函数
2. 把寄存器变量重命名为语义变量
3. 先正向跑一遍样例
4. 判断是写逆过程还是直接构造满足 compare 的输入

### 反推策略
- 逐步逆运算：xor、加减、swap、reverse 都容易逆
- 对不可逆部分：爆破单字节、约束求解、符号执行

---

## 9. 常见误区
- 一直在入口附近转，没找到最终 compare
- 太早陷入反编译细节，不先抓宏观数据流
- 看到加密 API 就以为必须密码学，实际 key/iv 都写死
- 盲目 patch，导致后面真实 flag 生成逻辑没执行

---

## 10. 最短作战模板

```text
1. strings + 导入函数 + main
2. 找输入点与比较点
3. 判断是简单变换、查表、加密、VM 还是壳
4. 能动调就直接在比较前取值
5. 能脚本还原就不要手算
6. patch 仅作为提速手段，不替代理解数据流
```
