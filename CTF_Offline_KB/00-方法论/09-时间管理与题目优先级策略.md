# 时间管理与题目优先级策略

## 1. 概述

CTF竞赛通常有严格的时间限制（24小时/48小时/或更短）。在有限时间内最大化得分，需要的不仅是技术能力，更是时间管理和题目优先级判断能力。在断网离线+小模型辅助的场景下，时间管理策略需要额外调整。

### 时间分配的黄金法则

```
经验法则：60-30-10法则
  60%的时间：深入解决核心题目（中高难度）
  30%的时间：快速收割简单题（建立优势）
  10%的时间：巡逻巩固（防止被超越）
```

### 各类题目的时间预算参考

| 题目类型 | 简单题时间预算 | 中等题时间预算 | 难题时间预算 |
|----------|---------------|---------------|-------------|
| Web | 30分钟 | 60-90分钟 | 120-180分钟 |
| Pwn | 45分钟 | 90-120分钟 | 180-240分钟 |
| Reverse | 30分钟 | 60-120分钟 | 120-240分钟 |
| Crypto | 20分钟 | 45-60分钟 | 90-120分钟 |
| Misc | 15-30分钟 | 30-60分钟 | 60-120分钟 |

## 2. 核心原理

### 2.1 题目优先级决策矩阵

```
                  高价值（高分）
                      │
      ┌───────────────┼───────────────┐
      │  第二优先级    │   第一优先级   │
      │  (团队最强领域) │  (立即投入)   │
      │               │               │
高难度 ────────────────┼──────────────── 低难度
      │               │               │
      │  第四优先级    │   第三优先级   │
      │  (最后处理)    │  (快速收割)   │
      │               │               │
      └───────────────┼───────────────┘
                      │
                  低价值（低分）
```

**第一优先级（立即投入）**：低难度+高分数 = "送分题"
- 特征：分值中等以上，看起来像常见漏洞类型
- 策略：全员投入，快速解决
- 时间：每题不超过60分钟

**第二优先级（主力攻克）**：高难度+高分数 = "决胜题"
- 特征：分值高，需要深度分析
- 策略：主力队员投入，其他队员辅助
- 时间：每题不超过180分钟

**第三优先级（快速收割）**：低难度+低分数 = "保底题"
- 特征：分值低，很明显是基础题
- 策略：新人/单人解决
- 时间：每题不超过30分钟

**第四优先级（最后处理）**：高难度+低分数 = "陷阱题"
- 特征：难度高但分数低
- 策略：先跳过，有剩余时间再碰
- 重要：出题人可能在误导

### 2.2 断网+小模型场景的时间分配调整

断网离线环境对时间管理的影响：

| 影响 | 调整策略 |
|------|----------|
| 无法实时搜索资料 | 每道题预留5-10分钟知识库检索时间 |
| 小模型推理慢 | 将模型查询放在后台，前台继续人工分析 |
| 工具加载慢（Docker启动等） | 赛中预启动常用Docker容器 |
| 无实时比分参考 | 基于本地进度评估，设定内部目标 |
| 无法下载新工具 | 赛前充分准备，赛中不浪费时间找工具 |

## 3. 关键技巧/检测方法

### 3.1 题目快速评估脚本

```bash
#!/bin/bash
# quick_evaluate.sh - 快速评估题目优先级

# 评估参数
DESCRIPTION="$1"  # 题目描述
SCAN_RESULT="$2"  # 扫描结果
ATTACHMENT="$3"   # 附件描述

SCORE=0  # 0-10分，越高越优先投入

echo "=== 题目快速评估 ==="

# 1. 检查是否有已知漏洞模式 (权重: 3)
KNOWN_VULNS=0
for pattern in "sql" "xss" "ssti" "lfi" "upload" "deserial" \
               "rce" "overflow" "format string" "rsa" "xor"; do
    if echo "$DESCRIPTION $SCAN_RESULT" | grep -qi "$pattern"; then
        KNOWN_VULNS=$((KNOWN_VULNS + 1))
    fi
done
if [ $KNOWN_VULNS -gt 0 ]; then
    SCORE=$((SCORE + 3))
    echo "[+] 已知漏洞模式: $KNOWN_VULNS 个匹配 (+3)"
fi

# 2. 检查是否有现成的工具/Exp (权重: 2)
if [ -f "./exp_db/$(echo "$DESCRIPTION" | md5sum | cut -c1-8).py" ]; then
    SCORE=$((SCORE + 2))
    echo "[+] 本地有现成Exp (+2)"
fi

# 3. 检查是否为团队擅长领域 (权重: 2)
# 这个需要根据实际情况调整
echo "[?] 是否为团队擅长领域？"
echo "    1=Web, 2=Pwn, 3=Reverse, 4=Crypto, 5=Misc"
read -p "    输入数字: " STRENGTH
if [ "$STRENGTH" = "1" ]; then  # 假设团队擅长Web
    SCORE=$((SCORE + 2))
    echo "[+] 团队擅长领域 (+2)"
fi

# 4. 评估复杂度 (权重: -2 或 +1)
echo "[?] 初步评估复杂度？"
echo "    1=简单(单一漏洞), 2=中等(两步利用), 3=困难(多步+绕过)"
read -p "    输入数字: " COMPLEXITY
case $COMPLEXITY in
    1) SCORE=$((SCORE + 1)); echo "[+] 简单题，可快速收割 (+1)" ;;
    2) echo "[*] 中等复杂度";;
    3) SCORE=$((SCORE - 2)); echo "[-] 高复杂度，谨慎投入 (-2)" ;;
esac

echo ""
echo "=== 评估结果 ==="
echo "优先级评分: $SCORE / 8"

if [ $SCORE -ge 5 ]; then
    echo "|| 建议: 【第一优先级】立即投入，30分钟内解决"
elif [ $SCORE -ge 3 ]; then
    echo "|| 建议: 【第二优先级】评估后投入，120分钟内解决"
elif [ $SCORE -ge 1 ]; then
    echo "|| 建议: 【第三优先级】空闲时快速收割"
else
    echo "|| 建议: 【暂时跳过】最后处理或放弃"
fi
```

### 3.2 时间追踪脚本

```bash
#!/bin/bash
# time_tracker.sh - 题目时间追踪

TRACKER_FILE="./time_tracker.log"

start_challenge() {
    local name="$1"
    local category="$2"
    local start_time=$(date +%s)
    
    echo "${start_time}|START|${category}|${name}" >> "$TRACKER_FILE"
    echo "[*] 开始计时: ${category} - ${name}"
    echo "    开始时间: $(date '+%H:%M:%S')"
}

end_challenge() {
    local name="$1"
    local result="$2"  # solved/abandoned
    local end_time=$(date +%s)
    
    echo "${end_time}|END|${result}|${name}" >> "$TRACKER_FILE"
    
    # 计算耗时
    local start_line=$(grep "START.*${name}" "$TRACKER_FILE" | tail -1)
    local start_time=$(echo "$start_line" | cut -d'|' -f1)
    local duration=$((end_time - start_time))
    local minutes=$((duration / 60))
    local seconds=$((duration % 60))
    
    echo "[*] 结束计时: ${name}"
    echo "    结果: ${result}"
    echo "    耗时: ${minutes}分${seconds}秒"
}

time_report() {
    echo "=== 时间追踪报告 ==="
    echo ""
    
    local total_start=$(head -1 "$TRACKER_FILE" | cut -d'|' -f1)
    local total_end=$(tail -1 "$TRACKER_FILE" | cut -d'|' -f1 2>/dev/null || date +%s)
    local total_duration=$((total_end - total_start))
    
    echo "比赛总时长: $((total_duration / 3600))时$(((total_duration % 3600) / 60))分"
    echo ""
    
    # 按题目统计
    echo "题目耗时统计:"
    local current_name=""
    local current_start=0
    
    while IFS='|' read -r timestamp type extra name; do
        if [ "$type" = "START" ]; then
            current_name="$name"
            current_start="$timestamp"
        elif [ "$type" = "END" ]; then
            local duration=$((timestamp - current_start))
            printf "  %-15s %-10s %3d分%02d秒\n" \
                "$current_name" "[$extra]" \
                $((duration / 60)) $((duration % 60))
        fi
    done < "$TRACKER_FILE"
    
    echo ""
    echo "建议时间分配: 60%核心题 + 30%简单题 + 10%巡逻"
}

# 使用方法
if [ "$1" = "start" ]; then
    start_challenge "$2" "$3"
elif [ "$1" = "end" ]; then
    end_challenge "$2" "$3"
elif [ "$1" = "report" ]; then
    time_report
else
    echo "用法:"
    echo "  $0 start <名称> <分类>   - 开始计时"
    echo "  $0 end <名称> <结果>     - 结束计时 (solved/abandoned)"
    echo "  $0 report               - 查看报告"
fi
```

### 3.3 比赛阶段时间分配策略

**比赛前15分钟：准备期**
```
[0:00-0:05] 验证环境、启动工具
  - 运行 verify_env.sh
  - 启动常用Docker容器（如Kali、靶场环境）
  - 打开终端多路复用器（tmux），预设布局

[0:05-0:10] 浏览全部题目
  - 阅读所有题目描述
  - 下载所有附件
  - 初步分类标注（Web/Pwn/Reverse/Crypto/Misc）

[0:10-0:15] 制定初步计划
  - 对每道题进行快速评估
  - 确定第一波攻击目标（2-3道优先题）
  - 分配队员任务
```

**比赛前30%时间：快速收割期**
```
目标：解决所有简单题和中等题
策略：
  - 优先做熟悉领域的基础题
  - 内部并行处理不同分类的题目
  - 遇到卡顿立即切换（不超45分钟）
  - 每解出1题，重新评估剩余题目的优先级
```

**比赛中间50%时间：核心攻关期**
```
目标：解决高价值中等题和难题
策略：
  - 集中2-3人攻克1道核心题
  - 另一人巡逻已解题（防止被攻击/检查flag有效性）
  - 每90分钟进行一次全局进度评估
  - 必要时调整策略（放弃某题转攻其他）
```

**比赛最后20%时间：巩固收尾期**
```
目标：提交、验证、补漏
策略：
  - 检查所有已提交flag是否仍然有效
  - 尝试攻克被跳过的题目
  - 用剩余时间猛攻1道高分题
  - 最后30分钟只提交flag，不再做新题
```

### 3.4 时间陷阱识别

```bash
#!/bin/bash
# time_trap_detector.sh - 识别可能的时间陷阱

echo "=== 时间陷阱识别检查 ==="

check_trap() {
    local description="$1"
    local score="$2"
    local solves="$3"
    
    TRAP_SCORE=0
    
    # 1. 高分但极少人解出 -> 可能是难题或不完整题目
    if [ "$score" -gt 300 ] && [ "$solves" -lt 3 ]; then
        TRAP_SCORE=$((TRAP_SCORE + 3))
        echo "[!] 高分低通过率 - 可能是极端难题"
    fi
    
    # 2. 描述中有"简单"但分值很高 -> 可能是误导
    if echo "$description" | grep -qiE 'easy|简单|基本|入门' && [ "$score" -gt 200 ]; then
        TRAP_SCORE=$((TRAP_SCORE + 2))
        echo "[!] 描述与分值不匹配 - 可能被误导"
    fi
    
    # 3. 需要特殊硬件/环境
    if echo "$description" | grep -qiE 'android|ios|arm|mips|firmware|driver'; then
        TRAP_SCORE=$((TRAP_SCORE + 3))
        echo "[!] 需要特殊环境/硬件 - 可能缺乏模拟环境"
    fi
    
    # 4. 涉及陌生技术栈
    if echo "$description" | grep -qiE 'blockchain|solidity|quantum|AI|ML'; then
        TRAP_SCORE=$((TRAP_SCORE + 2))
        echo "[!] 陌生技术栈 - 学习成本高"
    fi
    
    # 5. 需要猜测或爆破
    if echo "$description" | grep -qiE 'guess|brute|brute.force|枚举|爆破'; then
        if [ "$score" -lt 200 ]; then
            echo "[*] 可能需要爆破 - 成本可控"
        else
            TRAP_SCORE=$((TRAP_SCORE + 1))
            echo "[!] 高分但需爆破 - 可能时间不够"
        fi
    fi
    
    if [ $TRAP_SCORE -ge 4 ]; then
        echo ">>> 强烈建议: 暂时跳过此题！时间陷阱风险极高 <<<"
    elif [ $TRAP_SCORE -ge 2 ]; then
        echo ">>> 建议: 谨慎评估，设定时间上限后再投入 <<<"
    else
        echo ">>> 建议: 可以尝试投入 <<<"
    fi
}

# 交互式使用
echo ""
echo "请输入题目信息进行时间陷阱评估:"
read -p "题目描述: " DESC
read -p "分值: " SCORE
read -p "已解出人数(断网环境可估计): " SOLVES

check_trap "$DESC" "$SCORE" "${SOLVES:-0}"
```

## 4. 常见误区与注意事项

### 4.1 时间管理误区

| 误区 | 后果 | 正确做法 |
|------|------|----------|
| 上来就做最高分的题 | 可能卡死在难题上，浪费宝贵时间 | 先做简单的建立信心和节奏 |
| 一个人死磕一道题 | 该题可能根本就不在队伍能力范围内 | 设定时间上限，超时果断放弃 |
| 全员做同一道题 | 其他题目无人关注 | 按领域分工，定期同步进度 |
| 不关注时间流逝 | 比赛结束才发现还有简单题没做 | 设置定期提醒（如每30分钟检查进度） |
| 频繁切换题目 | 每次切换都有上下文切换成本 | 切换到新题后至少投入30分钟 |
| 忽视断网带来的时间成本 | 搜索资料、加载工具的时间被低估 | 赛中一切操作基于预装资源 |
| 不做笔记 | 重复分析和发现，浪费时间 | 每个发现都记录，队友可复用 |

### 4.2 断网环境的时间管理特殊点

```
时间浪费来源排查（断网场景）：
[ ] 等待本地知识库检索结果 (>30秒需要优化)
[ ] Docker容器冷启动 (>10秒可接受)
[ ] Python包导入慢 (预编译.pyc文件)
[ ] 词表加载慢 (使用预切片的小词表)
[ ] 小模型推理慢 (>60秒需要换更小的模型或简化Prompt)
[ ] 搜索本地文件系统 (使用locate/fd替代find)
```

## 5. 实战示例

### 示例1：24小时Jeopardy赛制的时间规划

```
假设：24小时比赛，20道题，5个分类，每分类4题。
分值分布：100, 200, 300, 500（每分类）
团队：3人（A擅长Web+Reverse, B擅长Pwn+Crypto, C擅长Misc+辅助）

=== 时间规划表 ===

[00:00-00:15] 环境准备+题目浏览     (15分钟)
  全员浏览题目，A做初步分类，B检查环境，C下载所有附件

[00:15-04:00] 快速收割期                (3.75小时)
  目标：拿下每分类的100分和200分题（10题，总分1500）
  A: Web(100,200) + Reverse(100,200)   → 目标4题
  B: Pwn(100,200) + Crypto(100,200)    → 目标4题
  C: Misc(100,200) + 支援A/B           → 目标2题

[04:00-16:00] 核心攻关期               (12小时)
  目标：攻克300分题，尝试500分题
  A+B: 合作攻克Web(300)+Pwn(300)
  C: Reverse(300)+Crypto(300)
  每2小时: 全员5分钟同步会议

[16:00-22:00] 巩固推进期                (6小时)
  目标：500分题，绕过被卡住的题
  A: Web(500)+Reverse(500) 尝试
  B: Pwn(500)+Crypto(500) 尝试
  C: Misc(300,500) + 检查所有flag有效性

[22:00-24:00] 收尾冲刺                   (2小时)
  目标：最后的机会
  - 提交所有未提交的flag
  - 解决遗漏的简单题
  - 每15分钟检查一次flag有效性
```

### 示例2：赛中实时调整示例

```
场景：比赛已进行3小时，进度如下

当前进度：
  Web-100: ✅ Solved (30分钟)
  Web-200: 🔄 In Progress (60分钟，卡住了)
  Pwn-100: ✅ Solved (45分钟)
  Pwn-200: ❌ 未开始
  Reverse-100: ✅ Solved (20分钟)
  Crypto-100: ✅ Solved (15分钟)
  Misc-100:   ❌ 未开始

分析：
  - Web-200卡了60分钟 -> 时间陷进预警！
  - Pwn-200还没开始，但B队员擅长Pwn -> 可以快速收割
  - Misc-100是简单题，浪费了未做

调整决策：
  1. A队员：放弃Web-200，转做Misc-100（预计20分钟解决）
  2. B队员：开始Pwn-200（预计60分钟解决）
  3. A队员完成Misc-100后：转Reverse-200
  4. Web-200：暂时搁置，2小时后再评估
```
